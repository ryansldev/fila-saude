---
title: Autenticação
description: Login do paciente (app) e da equipe (painel), e o token da TV.
---

A API tem três tipos de acesso. Cada rota da [referência](/docs/api/v1) diz qual pede, em
**Autenticação**.

## Paciente (app)

O paciente entra pelo CPF e senha na central, que vale para todos os municípios:

```http
POST /v1/auth/sign-in/username
Content-Type: application/json

{ "username": "12345678909", "password": "…" }
```

O token da sessão volta no cabeçalho `set-auth-token`. Nas rotas do paciente, mande-o em
`Authorization: Bearer <token>`. No app pela web, a sessão vai num cookie que a API define
(`better-auth.session_token`; em https, `__Secure-better-auth.session_token`).

CPF ou senha errados respondem 401 `invalid_credentials`.

O cadastro é `POST /v1/auth/sign-up/email`, com `name`, `cpf`, `email`, `phone`, `birthDate` e
`password`.

## Equipe (painel)

A equipe entra no painel do município (pelo subdomínio, ver [Municípios](/docs/municipios)):

```http
POST https://exemplo.<domínio>/v1/panel/auth/sign-in/username
Content-Type: application/json

{ "username": "gestor", "password": "…" }
```

A sessão fica num cookie que a API define (`fila-painel.session_token`; em https,
`__Secure-fila-painel.session_token`). Sem ele, toda rota do painel responde 401 `not_authenticated`,
antes de olhar o corpo ou os parâmetros. Com login, cada ação ainda confere a permissão do perfil na
unidade: sem ela, 403 `no_permission`.

## TV

A TV se registra em `POST /v1/tv` (pelo subdomínio do município) e recebe um código de 6 dígitos e um
token. A equipe pareia o código no painel; daí em diante a TV manda `Authorization: Bearer <token>` em
`GET /v1/tv/screen`.

## Senha errada e captcha

Ver [Limites](/docs/limites): depois de vários erros, o login bloqueia por um tempo ou pede captcha.

As rotas de login (`/v1/auth/*` e `/v1/panel/auth/*`) não estão na referência: os códigos delas estão
aqui, em [Erros](/docs/erros) e em [Limites](/docs/limites).
